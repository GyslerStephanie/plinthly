Data → engine → component architecture

What feeds what. One auditable dataset drives every pure‑function engine; components only render — they never hold the rule math.

One‑way dependency: data → engine → components → screen. No component contains rule math; every threshold lives in mortgage_rules so a regulation change is a one‑line edit. State lives only in App.jsx; AppStateContext is a read‑only derivation.

Key behaviours the diagram encodes

🔒 One gate, five children

goToPhase blocks any phase > 1 until a Phase 1 result exists; PhaseNav only re‑visits maxVisited. So qualification is the root of everything — the structural point the IA analysis flagged.

⟳ Live, no "run" button

Phase 1 recalculates on every keystroke (handleValuesChange → calculateAffordability); the result and the sticky bar update continuously.

↩ The one loop

Picking "renovate" in Phase 4 feeds a modelled net cost back into Phase 1 as an "effective property budget" — the only place the flow bends backward.

🔗 State = URL

No backend. syncHash writes inputs + phase to the URL on every change; decodeState restores them on load. The link IS the saved session.

🛡 Privacy by architecture

Nothing stored server‑side except language. Feedback POSTs only goal / strategy / free‑text — never financial inputs. Bank inquiry is a local mailto: draft that never auto‑sends.

🤖 Advisor rides along

Once a result exists, AdvisorFab is grounded by buildAdvisorContext (and the dream gap in Phase 2). The "independent advice" link is still a demand‑signal stub.
